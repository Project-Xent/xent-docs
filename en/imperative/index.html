Imperative UI Guide¶

The imperative track (fluxent.imp) gives your C23 program direct ownership over a retained XtkScene, atomic XtkTxn transactions, generated typed control wrappers in <xtk/xtk_controls.h>, and routed XtkEventFn callbacks.

The imperative API is also Xent’s stable C ABI surface: oxent (Rust), zxent (Zig), xenthon (Python), and hsxent (Haskell) all compile down to these functions.

Read the six chapters in sequence to go from basic window startup to 100,000-row virtualized collections and OS shell integration:

  1. 1. App, Host, & Scene Lifecycle — Initialize control modules, FluxApp, XtkHost, and XtkScene, dissect the fluxent.imp template, and shut down cleanly.

  2. 2. Atomic Transactions & Dynamic Subtrees — Build, reparent, reorder, and swap dynamic page subtrees atomically with XtkTxn, XtkNodeRef, XtkBatchResult, and XtkBatchDiag.

  3. 3. Typed Control Builders, Bitmasks, & Layouts — Master <xtk/xtk_controls.h> .set bitmasks, string length conventions, reusable Flex layout helpers, generic property queries, and composite data setters.

  4. 4. Event Routing, Frame Sync, & Change Stamps — Subscribe to capture/target/bubble event phases, decode XtkEventPayload variants, coalesce per-frame UI syncs with flux_app_onframe, and coordinate controlled inputs with XtkChangeStamp.

  5. 5. Imperative Virtualized Lists & Grouping — Drive 100,000-row ListView and GridView controls imperatively via XTK_EVENT_REALIZE, slot recycling, and sticky group headers.

  6. 6. Dialogs, Drag-and-Drop, Clipboard, & Windowing — Control modal ContentDialog instances, open native file dialogs, handle FluxData clipboard and drag-and-drop payloads, customize window chrome, and marshal worker-thread callbacks.
